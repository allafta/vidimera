# Deferral register

The living register of consciously deferred work, per the process discipline in
`docs/concept/SCOPING-GUIDE.md` section 7: every deferral carries the trigger that
un-defers it. An entry leaves this table only when the behavior lands or the
deferral is explicitly retired. Numbers are stable identifiers, not positions: a
gap is an entry that has left, and a new entry takes the next number never yet used.

| 12 | `finalize()`'s success batch is three SEQUENTIAL best-effort appends (chain-verify consultation, facts consultation, `confirmed`), not an atomic batch — SPEC §12's `appendBatch` is the all-or-nothing rung and is not part of the shipped `Store`. What it costs TODAY, after this build step's fix: a conflict on the second or third append throws a storage fault (it previously returned `record-not-open`). SPEC settles neither reading of that code here, and the silence is structural rather than an omission: SPEC's own finalize has no such shape. §9's rung (6) is "one atomic, variable-arity" `appendBatch(...)` — "all-or-nothing, so a conflict never leaves a partial tail" — and §12's batch "aborts the whole transaction with nothing applied". A mid-batch conflict with landed appends exists ONLY because this build substitutes three sequential `appendTransition` calls for that rung. What makes the old return wrong is therefore not a SPEC verdict but misrepresentation: a never-appends code carrying no `transitionRef` tells a host nothing was recorded, when consultations had landed. The throw leaves the one or two consultations that already landed on the chain with NO decision edge of that call's. Nothing rolls back — no rollback exists here — so what landed stays on the chain, and a retry that succeeds appends its own consultation pair on top rather than replacing it (after a second-append conflict that leaves THREE consultations, not two). Whether a retry is even possible depends on the state the conflicting writer left the record in, which the throwing call does not re-read and the throw therefore does not claim. ONE BOUNDARY INSIDE THIS ROW, recorded so it is auditable rather than folklore living in a comment: all three appends are storage faults under the same bound, yet the FIRST refuses `record-not-open` while the second and third throw. That is deliberate. At the first append nothing of the call has landed, so a never-appends code carrying no `transitionRef` still describes the call truthfully — but only for a `state-mismatch`; on the only Store that ships, a `seq` conflict there leaves the record `open` and the code false — `store/memory.ts` checks the state CAS BEFORE sequencing, so it raises `seq` only after finding the record `open`. That premise is `store/memory.ts`'s check order, NOT a SPEC §12 requirement, so a differently-ordered conforming adapter carries no such implication; `kernel/finalize.ts` states the same bound at the site, and this row does not paper over the residual.
